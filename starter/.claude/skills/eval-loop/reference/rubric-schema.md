# Rubric 的形狀與寫法

## JSON 結構

```json
{
  "name": "spec-resolution",
  "version": 1,
  "acceptance": "conjunctive",
  "criteria": [
    { "id": "c1", "text": "一個是／否問題" }
  ]
}
```

`acceptance` 只接受 `"conjunctive"`。harness 讀到別的值會直接拋錯 ——
加權平均會讓一個嚴重錯誤被幾個小優點抵銷。

`criteria[].mock` 是**離線假 judge 專用**的欄位，真的 judge 完全不看它。
不要在正式的 rubric 裡依賴它。

## 條目數量

**5–7 條是甜蜜點。** 超過 10 條，judge 的一致性會開始下降，而且維護不動。

## 寫一條的三個規則

1. **二元** —— 唸出來，答案必須是「有」或「沒有」。
2. **可引證據** —— judge 要能從輸入裡引一段原文來支持判定。
3. **獎勵做對，不獎勵寫多** —— 見下面那個陷阱。

## 四題檢查表

```
□ 1. 有明確的觸發時機（什麼時候要檢查這件事）
□ 2. 要觀察的東西，10 秒內能用眼睛或一個指令確認
□ 3. 兩個不同的人來檢查，會得到相同結論
□ 4. 它是二元的，不需要打分數
```

沒勾滿時的修法優先順序：

| 沒勾到 | 先做 |
|---|---|
| 第 4 題 | **最優先。**改成是／否的問法，其他三題通常跟著解決 |
| 第 2 題 | 加一個數字、閾值，或看得到的畫面條件 |
| 第 1 題 | 句首補 `WHEN …` 或 `GIVEN …` |
| 第 3 題 | 通常是用詞有歧義。把形容詞換成可以查的對象 |

## 一個符合全部規則、但仍然很爛的條目

```
報告長度在 300–800 字之間
```

它二元、可驗證、兩個人查會一樣 —— **四題全過。**

**但它在量長度**，所以它會直接獎勵冗長偏誤：被評估的東西會學會多寫一點就拿高分。

> **規則是過濾器，不是保證。** 每寫完一條，多問一句：
> **這條獎勵的是「做對」，還是「寫多」「寫得像專業人士」？**

## 改條目 vs 改標註

κ 不夠的時候，**永遠是改條目的用字**。

三種不一致，三種修法：

| 症狀 | 意思 | 修法 |
|---|---|---|
| judge 判 fail、你覺得該 pass | 條目寫得比你心裡的標準嚴 | 在條目裡補一個正例和一個反例 |
| judge 判 pass、你覺得該 fail | 條目有漏洞被鑽過去 | 把漏掉的對象明確寫進去 |
| 同一條跑兩次結果不同 | 條目定義不足 | **一定要重寫，而且通常要拆成兩條** |

**一次只改一條，然後重跑。** 一次改三條之後 κ 上升，你不知道是哪一條起作用，
下次遇到同樣問題你還是不會修。
