# 紀元轉換：換一把尺

「紀元」= 一段 rubric 被凍結的時期，凍結是為了讓分數可以互相比較。
「紀元轉換」= 把 rubric v(n) 升級成 v(n+1)。

**三個動作，按順序做。**

---

## 動作零（在跑之前）· 加對抗案例

找出**舊版判 accept、但你後來認為該 reject** 的案例，加成 `is_anchor: true`、
`expected_verdict: "reject"`、`is_adversarial: true`，並在 `note` 寫一句
「v1 accepted this; I disagree because ___」。

**必須在挑戰者被評分之前加。**

之後才加，等於在看過成績之後挑對挑戰者有利的考題。

> 這在修一個真實的偏誤：AI 審查器對 AI 產出的接受率會系統性偏高
> （RQGM 論文測到最高達人類產出的 1.91 倍）。對抗案例把「曾經被過度接受的東西」
> 變成明確的 reject 錨點，逼下一版學會擋它。

**一條都找不到也是合理結果**，代表舊版沒有明顯的過度接受。不要為了湊數硬找。

---

## 動作一 · 錨點閘門

**只在錨點上**跑兩個版本，比 κ。

```
promote  ⟺  κ_anchor(challenger) ≥ κ_anchor(incumbent)
```

**為什麼只用錨點：** 非錨點案例是在現任版本底下累積出來的，
用它們比較會偏向現任版本。錨點是唯一沒被任何一版影響過的東西。

> 論文用的是 ε-best-belief（`BB_ε(a) = I⁻¹_ε(1+S, 1+F)`，ε = 0.05）當閘門，
> 也就是保守估計下的成功率下界。這裡刻意簡化成直接比 κ ——
> 10 條錨點的規模下那個 Beta 後驗不會告訴你更多。**保留的是「不要用小樣本的
> 原始數字排名」這個習慣，不是那個公式。**

### 沒通過的時候

**那是一次成功的執行，不是錯誤。** 印出兩個數字，什麼都不改，正常結束。

**四個絕對不能做的動作：**

```
✗ 調閘門條件（「差 0.05 以內也算過」）
✗ 改那幾條錨點的標註
✗ 把挑戰者輸掉的錨點移出錨點集
✗ 加幾條挑戰者判得好的新錨點來稀釋
```

**最後一項最陰險，因為它看起來完全合理。**
分辨方法：**如果我還不知道挑戰者的分數，我還會想加這幾條嗎？**

正確的下一步：找出挑戰者輸在哪幾條錨點、它們有什麼共同點（通常是某一條改過頭了），
只改那一個地方，寫 v3 重跑閘門。

---

## 動作二 · 選擇性擦除

升級之後，把**舊版本的非錨點**執行結果標成 `stale: true`。

```
✗ 不要刪掉那些列
✗ 不要刪掉原始輸出
✗ 不要碰錨點的列
```

### 為什麼一定要做

不做的話，**舊排名會把新排名釘死**。

論文的對照組（不做擦除）在換掉評估器之後，排名的 Spearman ρ 停在 **≥ 0.90**
—— 排名幾乎沒變。**換了尺等於沒換。**

原因很直覺：如果有 100 筆舊分數和 25 筆新分數混在一起，
舊的在數量上就壓過新的了。任何排名、平均、趨勢圖，主導的都還是舊尺。

`stale` 這個旗標就是那個問題的解法。

### 為什麼保留原始輸出

**重新評分比重新執行便宜得多。** 想知道舊案例在新尺下幾分，
不需要重跑 agent —— 輸出還在，直接拿新版重判。

---

## 動作三 · 留下紀錄

不管有沒有升級，都要記一筆：

```
rubric_name, from_version, to_version,
anchor_kappa_from, anchor_kappa_to,
promoted (boolean), n_anchors, n_marked_stale, notes
```

**被擋下來的挑戰者也要記。** 那是有價值的結果 ——
它記錄了你曾經以為某個改動更好，而資料不同意。

---

## 執行順序總表

```
1. 加對抗案例（在評分之前）
2. dry-run：只在錨點上跑兩版，印出兩個 κ
3. 人工確認：錨點數對不對？它的升級判斷跟我自己比的一樣嗎？
4. 確認它不會動 eval_cases 的任何東西
5. --commit
6. 升級了 → 檢查 stale 標對了、錨點沒被標
   沒升級 → 寫下輸在哪幾條，不要動閘門
```
