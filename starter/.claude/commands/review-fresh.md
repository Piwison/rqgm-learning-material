審查目前的 diff。

## 先講清楚為什麼要在新 session 做這件事

**你如果剛寫完這段程式碼，你審不動它。** 你會記得每個決定的理由，
於是你會替它辯護，而不是挑戰它。

**所以這個 command 應該在一個乾淨的 session 裡跑**（`/clear` 之後，或另開一個分頁）。
如果你正在同一個 session 裡讀到這段 —— **先跟我說，我來決定要不要換。**

## 按這個順序審，不要跳

### 1. 它有做到當初說要做的嗎

先讀 spec / 設計共識 / issue。**逐條對照驗收條件。**

```
□ 每一條驗收條件都有對應的實作
□ 沒有做超出範圍的東西（做多了跟做少了一樣是問題）
```

### 2. 正確性

不要看風格，找**會壞的地方**：

- 邊界：空、null、0、超長、同時兩個、失敗重試
- 這段程式碼假設了什麼？那個假設什麼時候不成立？
- 錯誤處理是真的處理，還是只是 catch 起來吞掉？

### 3. 驗證是真的嗎

```
□ 測試有真的驗證行為，還是只是驗證「函式有被呼叫」？
□ 有沒有一個測試，我把實作改壞它會失敗？（想不出來就是沒測到）
```

### 4. 這裡面有什麼是我不會想到要問的

**這一條最有價值。** 你讀了完整的 diff，我沒有。
講一件我如果不看程式碼就不會發現的事。

## 輸出格式

```
## 沒做到 / 做超過
-（沒有就寫「無」）

## 會壞的地方
- 檔案:行號 — 什麼情況下會壞

## 驗證的漏洞
-

## 你應該知道但不會問的一件事
-
```

**不要給我「整體看起來不錯」。** 那句話沒有資訊量。
真的沒問題就寫「這四項我都查了，沒有發現」，並說出你**怎麼查的**。
