# 評估：沒有唯一正解的東西怎麼打分

**適用時機：** 輸出沒有標準答案，但你心裡有一把尺。
報告寫得好不好、spec 決議夠不夠具體、回覆的語氣對不對。

**不適用：** 有明確對錯的東西。那些用測試，不要用評估 —— 更快、更準、更便宜。

---

## 為什麼這件事值得花力氣

這個領域現在的共識大致是：**評估是瓶頸。**

Karpathy 在 Tesla 的說法是他大約 1/3 時間在資料、1/3 在評估、1/3 在其他所有事情，
而且好的評估非常難建 —— 要夠全面、有代表性、品質夠高，而且要能提供梯度訊號
（不能太簡單）。他後來也直接說現在有一場「評估危機」，因為公開基準會被過擬合。

**對你的意義：** 不要相信任何單一分數，包括你自己做出來的那個。
下面整套機制的存在，就是為了讓你能持續檢查那個分數有沒有在騙你。

---

## 五個零件

```
Rubric   一份有版本的二元條目清單
Judge    照著 rubric 打分的模型（必須跨家族）
Anchor   一小組你親手確認過的案例，只增不改，從不拿來優化
Epoch    rubric 被凍結的一段時期，凍結是為了分數可以互相比較
κ        judge 跟你的一致程度，扣掉碰巧一致的部分
```

---

## 四條規則

### 1. 跨家族判定

**judge 不能跟生成者是同一個模型家族。** 你用 Claude Code 生成，judge 就不能是 Claude。

模型會系統性偏好自己家族的產出。你的通過率會很漂亮，而且完全是假的。

**這條在 `eval/src/judge.ts` 裡是會拋錯的程式碼，不是文件上的一句話。**
文件裡的規則你半夜十一點會忘記。

### 2. 二元條目

每一條都是是／否。需要「打 8 分」就代表還沒拆解完。

### 3. 結合式接受

**全部通過才 accept。** 不要加權平均 —— 那會讓一個嚴重錯誤被幾個小優點抵銷。

### 4. 逐條引證據

每一條判定都要附輸入裡的原文引用。**沒有證據的判定是猜的，不是結果。**

要求引證據同時解決了兩件事：擋掉 judge 腦補，以及讓你可以抽查。

---

## κ：為什麼不能只看一致率

你和 judge 判了 20 條，一致 15 條 = 75%。**聽起來不錯。**

問題是：如果你們兩個都偏向 accept，那「一致」有一大部分是碰巧的。

極端情況：你 20 條全 accept、judge 也全 accept → 一致率 100%，
但這完全沒告訴你 judge 有判斷力。

**κ 就是在扣掉那個碰巧的部分。**

### 兩個算過的例子

| | 一致 | 一致率 | κ | 過關（≥0.6）？ |
|---|---|---|---|---|
| A | 15/20 | 75% | **0.50** | ✗ |
| B | 17/20 | 85% | **0.70** | ✓ |

**多對 2 條，κ 跳 0.20。**

這也是實務上工作的規模：**不是大改造，是找出那 2–3 條判錯的，看它們為什麼錯。**

> 這兩個數字在 `eval/src/kappa.test.ts` 裡是斷言。
> 測試紅了就代表這份文件在說謊 —— 先搞清楚哪邊錯了再往下走。

### 數字怎麼讀

| κ | 分級 | 意思 |
|---|---|---|
| < 0.20 | Slight | rubric 大概有根本性問題 |
| 0.21–0.40 | Fair | 有一點，但不能信 |
| 0.41–0.60 | Moderate | **最危險的區間** —— 看起來能用，其實不能靠 |
| **0.61–0.80** | **Substantial** | **目標** |
| 0.81–1.00 | Almost Perfect | 很好，但也懷疑一下案例是不是太簡單 |

分級出自 Landis & Koch (1977)。**它是慣例，不是物理定律** ——
不要為了 0.59 和 0.61 的差別爭論。

### 算不出來的時候

判定全部落在同一邊時，κ **沒有定義**。

harness 會印「算不出來」而**不是印 0**。那兩件事差很多，混在一起你會誤判 judge 壞掉。

---

## 那條唯一的規則

> **κ 不夠的時候，要改的是 rubric 的用字，永遠不是你的標註。**

改標註讓數字變好看，是這套東西裡你能做的最糟的一件事 ——
它把「檢驗工具」變成「自我安慰工具」，而且從此你再也不會知道自己的評估是不是在騙你。

**唯一的例外：** 你重看那條案例，發現自己當初真的標錯了（不是「新 rubric 這樣說比較好」，
是「我看漏了一句話」）。那種情況可以改，但必須在 commit message 和案例的 `note` 都留下說明。

**那個摩擦是刻意的。** 改標註應該讓你覺得麻煩，因為它應該很少發生。

---

## 換尺：紀元轉換

當 rubric 需要升級的時候，**不要直接換掉**。

```
1. 加對抗案例（舊版接受過、但你現在不同意的）—— 在評分之前加
2. 只在錨點上跑新舊兩版，比 κ
3. 新版 ≥ 舊版才升級
4. 升級後把舊版的非錨點結果標 stale（不刪任何東西）
5. 記一筆，包含沒通過的情況
```

**第 4 步不做的話，舊分數會把舊排名釘死** —— 換了尺等於沒換。

完整程序在 `.claude/skills/eval-loop/reference/epoch-transition.md`。

## 這套東西刻意不做的事

這是 RQGM 那篇論文的精簡版。**刻意跳過的部分：**

- 對 agent 變體做樹搜尋、維護一個 archive
- Thompson sampling on CMP
- UCB-Air 擴張門閥
- 在程式碼裡實作 ε-best-belief 反向 Beta 排序
- 指數間隔的分攤式重新評估檢查點
- 會自我修改的 Meta-Agent

**共同點：它們只在「大量自動產生的變體 + 長時間無人監督執行」的規模下才划算。**

**什麼時候該回頭看？** 一個具體的觸發條件：
**當你同時維護 5 個以上的變體、手動比較真的做不動的時候。**

## 反模式：這套迴圈會怎麼騙你

定期查這六項。**去看實際資料，不要憑印象。**

| 反模式 | 偵測方式 |
|---|---|
| **獎勵駭客** — 分數漲、品質沒動 | 通過率上升但錨點 κ 下降 → 你在鑽自己的指標 |
| **Judge 過度接受** | 塞一份你確定很爛的輸出進去。它照樣 accept 就是太鬆 |
| **錨點漂移** | `git log -p` 查標註有沒有被改過而且沒留紀錄 |
| **過擬合小評估集** | 案例的建立時間全部集中在同一天 → 評估集沒有從真實失敗長大 |
| **順序 / 冗長偏誤** | 有沒有條目在量長度？有做兩兩比較卻沒交換順序？ |
| **條目太模糊** | 同一批跑兩次，逐條結果不同 → 那條定義不足 |

**第 2 項的關鍵：通過率偵測不到 judge 變鬆。**
因為「品質變好」和「尺變鬆」在通過率上長得一模一樣。
所以要有一份固定的壞輸出（canary）每次都跑。
