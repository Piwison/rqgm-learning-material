# 驗證：怎麼確認它真的會動

**這份文件回答一個問題：什麼算證據？**

---

## 核心原則

> **「我讀過程式碼，看起來是對的」不是證據，是意見。**

模型很擅長宣告完成。它不是在騙你 —— 它是真的沒有執行過。
你要求的東西如果是「寫出正確的程式碼」，你得到的就是「看起來正確的程式碼」。

**改成要求執行結果，得到的東西就不一樣了。**

---

## 證據階梯

`/verify` 會要求模型說出它到了哪一階，以及為什麼只能到那一階。

| 階 | 證據 | 適用 |
|---|---|---|
| **1** | 自動化測試通過，而且**先看到它失敗過** | 有明確對錯的邏輯 |
| **2** | 真的執行指令，貼出完整輸出 | 腳本、CLI、資料轉換 |
| **3** | 真的打開頁面，附截圖或 DOM 查詢 | UI 變更 |
| **4** | 查詢真實資料，貼出查詢與回傳 | 資料庫變更 |
| **5** | 型別檢查 / lint 通過 | **這不算證明**，只代表能編譯 |

**目標不是永遠停在第 1 階。** 有些東西沒辦法自動測。
目標是**知道自己在第幾階**，而不是以為自己在第 1 階。

---

## 為什麼一定要先看到紅燈

一個從來沒失敗過的測試，和沒有測試，**在你眼裡長得一模一樣**。

實務上最常見的假綠燈：

```
✗ 測試斷言的是「函式有被呼叫」，不是「結果是對的」
✗ 測試把實作邏輯抄了一遍，所以實作錯了測試也跟著錯
✗ 測試 mock 掉了真正會出事的那一段
```

**檢查方法（10 秒）：** 把實作故意改壞一行，測試應該要紅。
不紅的話，那個測試沒有在測你以為它在測的東西。

---

## 給 AI 寫的程式碼特別要看的三件事

### 1. 錯誤處理是真的處理，還是吞掉

```ts
try { await doThing(); } catch (e) { /* ignore */ }
```

這種東西模型很容易寫出來，而且它會讓所有測試都通過。
**問一句：這個 catch 吞掉的錯誤，我要多久才會發現？**

### 2. 它有沒有「順手」改了你沒要求的東西

尤其是**資料**和**設定檔**。

程式碼改壞了會有測試擋；**資料被順手「整理」過，通常沒有任何東西會擋。**

> 這就是為什麼 `eval/` 的 harness 裡寫死了一條「絕不寫入 cases/」——
> 那是 ground truth，被動到就回不來了。

### 3. 它有沒有把 `null` 當成 0

```
成本未知 → cost_usd = null   ✓
成本未知 → cost_usd = 0      ✗ 會讓你的節省數字變漂亮而且錯誤
```

**「不知道」和「零」是兩件事。** 混在一起的時候，錯誤的方向永遠是對你有利的那邊
—— 所以你不會發現。

## 驗證和評估的差別

這兩個詞很容易混，但它們處理的是不同的問題：

| | 驗證（Verification） | 評估（Evaluation） |
|---|---|---|
| 問的問題 | 這一次做對了嗎 | **這一類**做得多好 |
| 答案形狀 | 是／否 | 一個分佈、一個比率 |
| 工具 | 測試、執行輸出、截圖 | rubric、judge、κ |
| 什麼時候用 | 每一片切片做完 | 輸出沒有唯一正解的時候 |

**有唯一正解的東西不需要評估，用測試就好。**

評估是給「報告寫得好不好」「這條 spec 決議夠不夠具體」這種
**沒有唯一正解、但你心裡有一把尺**的東西用的。

→ 那把尺怎麼建，看 `02-evaluation.md`。
