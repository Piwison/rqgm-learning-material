開場

為什麼你讀不下去那篇論文

約 10 分鐘 · 讀完再往下

先說結論：這不是你的問題，是讀法的問題。

RQGM 那篇論文是寫給 ML 研究者的。它預設讀者已經熟悉樹搜尋、多臂拉霸機、Beta 後驗分佈、自我修改程式碼。它不會停下來解釋這些，因為它的目標讀者不需要。

但這裡有一個關鍵事實：這篇論文真正的想法，完全不需要那些數學。

整篇論文的核心，一句話

如果你的評分標準永遠不變，被你評分的東西遲早會學會鑽這個標準的漏洞。所以標準也必須進化 —— 但要有紀律地進化，不然你會失去比較基準。

這句話你聽得懂。你在審 spec 的時候早就知道了：如果 RD 摸清了你只看某三件事，他們就只會做好那三件事。

論文剩下的 40 頁，是在回答「怎麼有紀律地改標準」這個工程問題。那些數學是手段，不是重點。

這週的三條規則

規則一：你這週不會完整讀那篇論文。前四天完全不碰它。第五天才第一次打開，而且只讀四個地方（Lesson 4 會給你精確座標）。

規則二：所有概念先從你自己的工作裡長出來。你每次審 YCM 的 TBD 決議、每次打回一個 YCO 原型，那都是評估。我們要做的不是教你新東西，是把你已經在做的事寫下來、變成可重複的。

規則三：遇到不懂的詞就跳到術語表，看完就回來。不要停下來 Google —— 術語表已經幫你篩過，只留這週真的會用到的 14 個。

開始前

14 個你會一直看到的詞

不用背 · 看不懂就翻回這裡

這些詞在後面會反覆出現。先掃一遍有印象就好，遇到再回來查。

Agent智慧體
一個會自己決定下一步要做什麼的 AI 程式。跟單次問答的差別是：它會連續做好幾個動作 —— 查資料、呼叫工具、再根據結果決定下一步。你的 YCO 膚況報告流程就是一個 Agent。
Rubric評分準則
一張檢查清單，列出「什麼才算做對」。跟你 spec 裡的驗收條件是同一種東西 —— 只是寫成讓機器也能照著跑的形式。
Judge裁判
照著 rubric 打分的那一方。可以是人，也可以是另一個 AI。這門課大部分時候指後者。
錨點Anchor
一小批你親手確認過答案的案例，而且之後不再更動。它的用途只有一個：當你想換一把新的尺，先拿這批已知答案考它 —— 考得比舊尺好才准換。沒有錨點，標準演化就會變成自說自話。
Pass rate通過率
一批案例裡有多少比例被判定為「通過」。注意：pass rate 上升不代表品質變好，可能只是 Agent 學會鑽標準的漏洞 —— 這是整門課要防的第一件事。
API
兩個程式之間互相呼叫的窗口。「呼叫膚況偵測 API」＝ 你的程式把照片丟給另一個服務，那個服務把偵測結果丟回來。像叫外送：你下單、對方送貨，你不用管廚房怎麼運作。
JSON
一種寫結構化資料的格式，長得像 { "名稱": "值" }。之所以要求 AI 用這格式回答，是因為這樣程式才能直接讀，不用去猜它那段自然語言在講什麼。你不用會寫，看得懂大括號裡是「欄位：內容」就夠。
Claude Code
Anthropic 的命令列版 Claude，可以直接讀寫你電腦上的檔案、跑指令。這門課裡「貼進 Claude Code」的意思是：把那段指令貼給它，讓它幫你寫檔案。你已經在用了。
TypeScript
一種程式語言（JavaScript 的加強版）。你不用會寫 —— 課程裡你只需要能讀懂 AI 寫出來的東西大概在做什麼，以及在它做錯時說「這裡不對」。
npm run eval
一行啟動指令。npm 是 JavaScript 世界的工具管理器，run eval 是「跑那個叫 eval 的流程」。你只要記得：這行打下去，整批評估就會自動跑完。
部署 / DeployVercel
把你電腦上的網頁放到網路上，讓別人用網址就能打開。Vercel 是做這件事最省事的服務之一 —— 接上你的專案，它會給你一個網址。
Cohen's κkappa
衡量兩個判斷者有多一致的分數，範圍大致 0 到 1。它比「同意百分比」好，因為它扣掉了「隨便亂猜也會猜對」的部分。Week 2 的關卡是 κ ≥ 0.6。κ 是希臘字母 kappa，唸「卡帕」，不用怕。
Epoch紀元
一段評分標準保持不動的期間。標準只在紀元與紀元的交界處才允許更換 —— 這樣紀元內部的分數才有可比性。
Reward hacking獎勵駭客
被評分的一方學會鑽指標的漏洞，分數一路漲但實際能力沒進步。這是所有評估系統的頭號敵人，也是 RQGM 存在的理由。

Lesson 0

先做這件事

30 分鐘 · 動手為主

在讀任何東西之前，先產出素材。這 30 分鐘的產出會被後面每一課用到，也會變成你 Week 2 的錨點集。

動手

回想過去兩週，寫下 3 個你做過的「接受 / 拒絕」判斷。可以是一條 YCM 的 TBD 決議、一個 YCO 原型、或一份 RD 的 handoff 實作。

關鍵動作：把「為什麼」再逼問一層

寫完第一層理由後，對每一個問自己：如果換一個人來審，他會做出跟我一樣的判斷嗎？

如果答案是「不一定」，代表你的理由裡有隱含的東西沒說出口。把它挖出來 —— 那就是你 rubric 缺的那一條。

案例　TBD-MV-03 的決議

判斷　拒絕

為什麼 v1　它寫「播放體驗要流暢」，但沒有人能驗證什麼叫流暢。

這一課在做什麼

你剛剛做的事情有個名字：把隱性判斷顯性化。你腦中有一把尺，但那把尺目前只存在你腦中 —— 所以它無法被重複、無法交給機器、無法在你休假時繼續運作。

Lesson 1

評估的兩種看法

2 小時 · 概念 + 動手

看結果，還是看過程？這是評估設計裡第一個、也是最常被搞混的分岔。

假設你要評估 YCO 的膚況報告 Agent。它做的事情大概是這樣：

方式 A — 看結果（Outcome Evaluation）

只看最後那份報告。它讀起來合理嗎？建議的產品對得上偵測到的問題嗎？語氣會不會太嚇人？

方式 B — 看過程（Process / Trajectory Evaluation）

看它中間做了什麼。它有沒有真的呼叫偵測 API？還是憑照片「看起來像」就編了？它查產品目錄了嗎？還是直接寫出一個目錄裡根本沒有的產品？

先自己想 30 秒

一份報告，可以「結果正確但過程錯誤」嗎？

答案是可以，而且很常見 —— 就是圖 1 下半部那條路徑。Agent 沒有呼叫偵測 API（可能超時失敗了），但它從照片的整體色調猜「這個人應該有泛紅問題」，然後推薦了一款鎮定精華。結果剛好對了。你看報告，完全看不出問題。

只看結果，你會給它 PASS。但這個 Agent 其實是壞的，只是這次運氣好。下次遇到一個膚況不典型的使用者，它就會胡說八道，而且你的評估系統會完全沒有預警。

這就是為什麼「只看結果」的評估會系統性高估 Agent 的能力。

反過來也會出錯

那全部改成看過程呢？也不行。Agent 可能完美地呼叫了每一個 API、走完每一步，但最後那份報告寫得像醫學論文，使用者根本看不懂。過程全對，結果沒用。

實務上怎麼選

情境主要看理由
有明確對錯（程式碼能不能跑、證明對不對）結果結果本身就是硬證據
沒有唯一正解（報告、文案、spec）結果為主 + 少量過程過程無法窮舉，但關鍵步驟要抽查
除錯 / 找出「為什麼會錯」過程只有過程能告訴你錯在哪一步
上線後的持續監控結果 + 關鍵步驟旗標過程全記成本太高

你 Week 1 的第一隻 Agent 會是純結果評估，因為它最簡單。過程評估留到 Week 3。

動手：套用到你的案例

回到 Lesson 0 那三個案例。對每一個問：我當時是在看結果還是過程？如果只看另一邊，我的判斷會改變嗎？

兩個常見誤解

「過程評估比較高級。」不是。它比較貴、比較難定義「正確的過程」，而且很多任務根本沒有唯一正確的過程。它是工具，不是目標。

「看結果 = 看最終輸出的字面內容。」不完全是。「結果」指的是任務有沒有達成。對編程 Agent 來說，結果是「測試有沒有過」，不是「程式碼看起來漂不漂亮」。

Lesson 2

LLM 當裁判：它會怎麼騙你

2 小時 · 概念 + 自我測驗

你不可能每次都親自看 200 份報告。所以做法是：寫一份rubric（評分準則），讓另一個 LLM 照著它幫你打分。這叫 LLM-as-a-Judge。

先講清楚：rubric 是什麼

就是一張檢查清單，列出「什麼才算做對」。跟你 spec 裡的驗收條件是同一種東西 —— 只是寫成讓機器也能照著跑的形式。Lesson 3 會完整處理怎麼寫，這一課你只要知道「裁判是照著一張清單在打分」就夠。

好消息是它真的有用。2023 年的一項經典研究（Zheng et al., MT-Bench）發現，強模型當裁判時，與人類判斷的一致率超過 80% —— 這個數字大約等同於兩個人類之間的一致率。換句話說：一個好的 LLM 裁判，跟你找另一個同事來審，準確度差不多。

壞消息是它有四種系統性偏誤。不是偶爾出錯，是穩定地往同一個方向歪。

四種偏誤

1. 位置偏誤（Position Bias）

2. 冗長偏誤（Verbosity Bias）

它偏好比較長的答案，即使長的那個並沒有多說什麼有用的東西。這個偏誤特別危險，因為它會讓 Agent 學會「多寫一點就會拿高分」，然後你的 YCO 報告會越來越囉唆，而分數持續上升。

怎麼防：用二元條目。「有沒有列出至少兩個偵測到的膚況問題」這題，寫 50 字和寫 500 字的答案是一樣的判定。

3. 自我偏好偏誤（Self-Preference Bias）

它偏好自己家族模型產生的內容。這是四種裡最陰險的一種。如果你用 Claude 生成報告、又用 Claude 當裁判，裁判會系統性地給高分。你的通過率會很漂亮，而且完全是假的。

RQGM 論文的實測

最強的基準審查器，對 AI 寫的論文的接受率高達對人類論文的 1.91 倍。同樣品質，只因為是 AI 寫的就更容易被接受。

怎麼防：用不同家族的模型當裁判。這是整套系統裡最便宜、效果最大的一條規則。生成用一家，評分用另一家。

4. 校準不良（Poor Calibration）

它說「我 90% 確定」的時候，實際正確率可能只有 60%。信心程度跟實際準確度對不上。

怎麼防：不要問它「你多有信心」，改問「這一條有沒有通過，並引用原文證據」。要求引證據，會逼它停止憑感覺。

自我測驗：認出偏誤

四個情境，各選一個答案。答錯不會怎樣 —— 答錯的地方才是真正學到的地方。

從偏誤反推：rubric 的三條設計規則

規則一：條目要二元（Binary）

壞好
這份報告的建議是否恰當？每一個推薦的產品，是否都對應到報告中明確提到的一個膚況問題？（是／否）

二元條目不受長度影響、不受語氣影響，而且兩個人（或兩次執行）比較容易得到相同結果。

規則二：證據約束（Evidence-Bounded）

要求裁判只能根據眼前的輸出做判斷，並且引用原文。它的回答會長這樣（這就是 JSON 格式）：

{ "criterion": "每個推薦都對應到偵測到的問題",
  "verdict": "fail",
  "evidence": "報告推薦了『深層修護面膜』，但偵測結果只有毛孔與泛紅，
               沒有任何一項對應到『修護』。" }

看不懂大括號沒關係 —— 重點只有一個：它必須指出「哪一句話」讓它做出這個判定。強制引證據，可以擋掉裁判自己腦補上下文的「幻覺性判定」。

規則三：結合式接受（Conjunctive）

所有條目都通過，才算 accept。不要用加權平均 —— 因為加權平均允許「一項嚴重錯誤被幾項小優點抵銷」。一份編造了不存在產品的報告，不該因為語氣親切就及格。

常見誤解

「用最強的模型當裁判就好了。」最強的模型一樣有這四種偏誤。強模型只是比較準，不是比較沒偏見。跨家族比用更強的模型重要。

Lesson 3

從 spec 到 rubric：你早就會了

1.5 小時 · 動手為主

你 Notion 裡那份「Claude Project Scaffold」寫著一句話：State, in one line, how you will VERIFY the work. 那句話就是 rubric 的定義。

Spec 世界評估世界
驗收條件（Acceptance Criteria）Rubric 條目（Criterion）
TBD-MV-01 已解決這個案例 pass
Spec review 打回判定 reject
Spec v1.2Rubric version 2
Handoff 給 RD把 rubric 交給裁判執行

所以你不是在學一個新技能。你是在學如何把一個你已經每天在做的動作，寫成機器可以重複執行的形式。

兩種寫法，挑一種用熟

EARS 句型（適合功能規格）

WHEN <觸發條件>, THE <系統> SHALL <可觀察的行為>

WHEN 使用者在 MV 播放中切換歌曲,
THE 播放器 SHALL 在 300ms 內顯示新 MV 的首幀。

Given / When / Then（適合流程與 Agent 行為）

GIVEN 膚況偵測回傳了「毛孔 0.7、泛紅 0.4」
WHEN Agent 生成報告
THEN 報告中每一個推薦產品，都對應到這兩項其中之一

兩種都可以，挑一種用到熟為止。混用會讓後面的 rubric 難以維護。

作業 L3 · 五條改寫—
TBD ID原始決議改寫後沒過第幾題

兩個常見誤解

「所有東西都能寫成二元條件。」不能。有些東西本質上是程度問題（例如「這段文案吸引人嗎」）。做法不是硬掰成二元，而是拆解：把「吸引人」拆成「開頭 15 字內有具體利益」「沒有出現三個以上的形容詞堆疊」等可檢查的代理指標。

「寫越細越好。」不是。一條 rubric 有 5–7 個條目通常剛好。超過 10 條，裁判的一致性會開始下降，而且你自己也維護不動。

三次掃描法

第一次（20 分）只讀 Abstract、Introduction、所有圖的標題與說明文字、Conclusion。讀完要能回答：它說現有做法有什麼問題？解法一句話是什麼？宣稱改善多少？不要停下來查任何看不懂的名詞。

第二次（40 分）把目錄抄下來，每一節旁邊寫一句「這節在解決什麼問題」。只讀每節首段與末段。遇到公式：跳過。

第三次（30 分）只深讀四個地方：Controlled Utility Evolution（紀元機制）、Selective Erasure + Figure 3、§5 對抗性除偏 + Figure 6、四個 Anchor 的介紹段落。

兩個符號值得多花五分鐘

CMP 和 BB_ε 這兩個，Week 2 之後你會一直碰到。這裡各給一個小數字的例子，看完就懂了。

CMP · 為什麼要看「整個家族」

Agent A 自己只過 3/5（看起來 60%），但它生出來的兩個後代表現很好：8/10、9/10。
整個家族合計：成功 3+8+9 = 20，失敗 2+2+1 = 5 → CMP = 20/25 = 80%

Agent B 自己過 4/5（看起來 80%），但後代都掛了：1/10、2/10。
整個家族合計：成功 4+1+2 = 7，失敗 1+9+8 = 18 → CMP = 7/25 = 28%

B 單看自己贏（80% vs 60%），但 A 才是好得多的下注（80% vs 28%）。這叫 Metaproductivity–Performance Mismatch。用在你身上：一個 prompt 版本自己跑得好，不代表基於它改出來的下一批也會好。

BB_ε · 為什麼不能相信小樣本

X 跑了 1 次，1 勝 0 敗 → 通過率 100%
Y 跑了 20 次，18 勝 2 敗 → 通過率 90%

直覺排名會選 X。但把「樣本太小」這件事算進去，取一個保守下限（95% 把握之下至少有多少）：
X → 約 22%　　Y → 約 74%

保守估計正確地把 Y 排在 X 前面。你不需要會算這個數字（控制台的實驗室分頁有現成的滑桿）。你要帶走的是那個習慣：永遠不要用小樣本的原始通過率排名。

這是一篇 2026 年 6 月的 preliminary preprint（作者自己這樣定義）。單次執行、搜尋視野短。它的概念是可靠的，但所有數字都應該視為暫定。

這件事本身就是一課：二手摘要會夾帶。你剛學的「證據約束審查」原則 —— 只根據眼前的原文做判斷、要求引證據 —— 第一個該用在你自己的閱讀上。

Part B · 第一隻 Agent：Spec-Resolution Judge（3 小時）

這隻 Agent 只做一件事：判斷你的 spec 決議有沒有包含「可在 10 秒內驗證的條件」。它會用到你 L3 那份五列表格 —— 但這次是讓 AI 來判，然後你去對照它跟你的判斷差多少。

開始前先想 60 秒

在跑之前，先自己預測：你那 5 條決議裡，你覺得 AI 會判幾條 FAIL？

這個動作叫「預測 - 對照」。只有在你的預測被打臉的時候，你才會真的記住 —— 這是這一課最重要的機制，不要跳過。

執行

打開 Claude Code，開一個新的 session（不要跟你在改 YCM codebase 的那個混在一起），把下面整段貼進去，然後把 L3 表格的內容也貼給它。

Claude Code prompt · spec-judge
GOAL: Build a small evaluation agent called "spec-judge" that grades whether my
resolved YCM spec items actually meet a verifiable acceptance criterion. I drive
Claude Code and review code — keep it a single readable TypeScript script, no framework.

INPUT: I will paste 8-12 of my real resolved TBD-items. Each has: an ID
(e.g. TBD-MV-01), the resolution text, and (if present) an acceptance/verification line.

WHAT TO BUILD:
1. A script `spec-judge.ts` that takes a JSON array of items and, for each, asks an
   LLM judge to decide PASS/FAIL on this single question: "Does this resolution
   contain a criterion that a reviewer could verify in under 10 seconds by looking
   at the product or code?"
2. The judge must output strict JSON: { id, verdict: "PASS"|"FAIL",
   reason: "<one sentence>", suggested_criterion: "<if FAIL, a rewrite that WOULD
   be verifiable, in EARS or Given/When/Then form>" }.
3. Use a model from a DIFFERENT family than whatever wrote the specs, to reduce
   self-preference bias. State which model you're using and why.
4. Print a summary table: PASS count, FAIL count, and the list of suggested_criteria
   for the fails.
5. Save the output to `spec-judge-report.md`.

CONSTRAINTS:
- Do NOT touch any other files. This is a standalone artifact.
- Before writing code, restate in ONE line how you will VERIFY the script works,
  then write a 2-line sample input and show me the expected output shape.

ACCEPTANCE CRITERIA (my rubric for YOUR work):
- The script runs on my pasted items without errors.
- Every FAIL comes with a concretely better, verifiable criterion.
- The report is a markdown file I can skim in 60 seconds.

執行後最重要的一步

不要只看報告就收工。逐條對照：AI 的判斷和你的判斷，哪幾條不一樣？對每一條不一樣的問自己：是 AI 錯了，還是我的標準其實沒說清楚？

這是整週最有價值的一題

如果 AI 判 FAIL 而你覺得該 PASS，通常代表你腦中有一個沒寫出來的補充條件。把它挖出來寫下來 —— 那就是你 rubric 缺的那一條。

把結果記進台帳，順便認識 κ

打開你的 RQGM 控制台 → 台帳分頁，每一條決議加一筆案例，填你的判定和 AI 的判定，最有把握的幾條標成錨點。記完之後首頁的 κ 就會亮起來。
