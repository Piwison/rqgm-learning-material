# Week 1 教材 · AI Agent 評估的地基

**給非工程背景學習者的第一週。** 約 11–12 小時，分 6 課。

---

## 開場：為什麼你讀不下去那篇論文

先說結論：**這不是你的問題，是讀法的問題。**

RQGM 那篇論文是寫給 ML 研究者的。它預設讀者已經熟悉樹搜尋、多臂拉霸機（bandit）、Beta 後驗分佈、自我修改程式碼。它不會停下來解釋這些，因為它的目標讀者不需要。

但這裡有一個關鍵事實：**這篇論文真正的想法，完全不需要那些數學。**

它的核心主張可以用一句話講完：

> 如果你的評分標準永遠不變，被你評分的東西遲早會學會鑽這個標準的漏洞。所以標準也必須進化 —— 但要有紀律地進化，不然你會失去比較基準。

這句話你聽得懂。你在審 spec 的時候早就知道了：如果 RD 摸清了你只看某三件事，他們就只會做好那三件事。

論文剩下的 40 頁，是在回答「**怎麼有紀律地改標準**」這個工程問題。那些數學是手段，不是重點。

### 這週的三條規則

**規則一：你這週不會完整讀那篇論文。** 前四天完全不碰它。第五天才第一次打開，而且只讀四個地方（Lesson 4 會給你精確座標）。

**規則二：所有概念先從你自己的工作裡長出來。** 你每次審 YCM 的 TBD 決議、每次打回一個 YCO 原型，那都是評估。我們要做的不是教你新東西，是把你已經在做的事**寫下來、變成可重複的**。

**規則三：遇到不懂的數學符號，先跳過。** 我會在 Lesson 4 給你一份對照表，把論文裡的符號翻成人話。在那之前，看到公式就跳過，不要停。

# Lesson 0 · 先做這件事（30 分鐘）

**在讀任何東西之前，先產出素材。** 這 30 分鐘的產出會被後面每一課用到，也會變成你 Week 2 的錨點集。

## 動手

打開一個空白文件。回想過去兩週，寫下 **3 個你做過的「接受 / 拒絕」判斷**。可以是：

- 一條 YCM 的 TBD 決議，你覺得可以收掉 / 或退回去重寫
- 一個 YCO 原型，你 approve 了 / 或打回
- 一份 RD 的 handoff 實作，你驗收通過 / 或退回

每一個寫三行：

```
【案例】TBD-MV-03 的決議
【我的判斷】拒絕
【為什麼】它寫「播放體驗要流暢」，但沒有人能驗證什麼叫流暢。
```

## 現在做這件事：把「為什麼」再逼問一層

看你剛寫的三個「為什麼」。對每一個問自己：

> **如果換一個人來審，他會做出跟我一樣的判斷嗎？**

如果答案是「不一定」，那代表你的理由裡有隱含的東西沒說出口。把它挖出來、寫下來。

例如上面那條，挖深一層可能變成：

```
【為什麼 v2】「流暢」沒有定義閾值。可驗證的版本應該是：
「切換 MV 時，首幀出現時間 < 300ms」。我拒絕它是因為它缺一個數字或一個
可以在 10 秒內用眼睛確認的條件。
```

## 這一課在做什麼

你剛剛做的事情有個名字：**把隱性判斷顯性化（externalizing tacit judgment）**。

這是整個 AI Agent 評估的起點。你腦中有一把尺，但那把尺目前只存在你腦中 —— 所以它無法被重複、無法交給機器、無法在你休假時繼續運作。

接下來六週要做的所有事，本質上都是同一件：**把你腦中那把尺搬出來，變成一個有版本、可被檢驗、也可能被推翻的東西。**

> **檢核點：** 你手上現在應該有 3 個案例、每個有兩層「為什麼」。有的話就往下走。

# Lesson 1 · 評估的兩種看法（2 小時）

## 核心概念：看結果，還是看過程

假設你要評估 YCO 的膚況報告 Agent。它做的事情大概是：

```
使用者上傳照片
   → Agent 呼叫膚況偵測 API
   → 拿到「毛孔粗大 0.7 / 泛紅 0.4 / 細紋 0.2」
   → 查產品目錄
   → 生成一份報告
```

你有兩種評估方式：

**方式 A — 看結果（Outcome Evaluation）**
只看最後那份報告。它讀起來合理嗎？建議的產品對得上偵測到的問題嗎？語氣會不會太嚇人？

**方式 B — 看過程（Process / Trajectory Evaluation）**
看它中間做了什麼。它有沒有真的呼叫偵測 API？還是憑照片「看起來像」就編了？它查產品目錄了嗎？還是直接寫出一個目錄裡根本沒有的產品？

## 為什麼這個區分很重要

先自己想 30 秒：**一份報告可以「結果正確但過程錯誤」嗎？**

<br>

答案是可以，而且很常見。舉一個具體的：

> Agent 沒有呼叫偵測 API（可能超時失敗了），但它從照片的整體色調猜「這個人應該有泛紅問題」，然後推薦了一款鎮定精華。**結果剛好對了** —— 那個人確實泛紅。你看報告，完全看不出問題。

只看結果，你會給它 PASS。但這個 Agent 其實是壞的，只是這次運氣好。下次遇到一個膚況不典型的使用者，它就會胡說八道，而且你的評估系統會完全沒有預警。

**這就是為什麼「只看結果」的評估會系統性高估 Agent 的能力。**

## 反過來也會出錯

那全部改成看過程呢？也不行。

> Agent 完美地呼叫了每一個 API、走完每一步，但最後那份報告寫得像醫學論文，使用者根本看不懂。過程全對，結果沒用。

## 實務上怎麼選

| 情境 | 主要看 | 理由 |
|---|---|---|
| 有明確對錯（程式碼能不能跑、數學證明對不對） | 結果 | 結果本身就是硬證據 |
| 沒有唯一正解（報告、文案、spec） | 結果為主 + 少量過程 | 過程無法窮舉，但關鍵步驟要抽查 |
| 除錯 / 找出「為什麼會錯」 | 過程 | 只有過程能告訴你錯在哪一步 |
| 上線後的持續監控 | 結果 + 關鍵步驟旗標 | 過程全記成本太高 |

**你 Week 1 的第一隻 Agent 會是純結果評估**，因為它最簡單。過程評估留到 Week 3。

## 動手：套用到你的案例

回到 Lesson 0 那三個案例。對每一個問：

1. 我當時是在看**結果**還是看**過程**？
2. 如果只看另一邊，我的判斷會改變嗎？

寫下答案。這裡沒有標準答案，重點是你開始有意識地分辨這兩層。

## 常見誤解

**誤解一：「過程評估比較高級。」**
不是。過程評估比較貴、比較難定義「正確的過程」。很多任務根本沒有唯一正確的過程。它是工具，不是目標。

**誤解二：「看結果 = 看最終輸出的字面內容。」**
不完全是。「結果」指的是**任務有沒有達成**。對編程 Agent 來說，結果是「測試有沒有過」，不是「程式碼看起來漂不漂亮」。

> **檢核點：** 用你自己的話，向一個沒學過的人解釋「為什麼只看結果會高估 Agent 能力」。講得出來就往下走。

# Lesson 2 · LLM 當裁判：它會怎麼騙你（2 小時）

## 為什麼要用 LLM 當裁判

你不可能每次都親自看 200 份報告。所以做法是：**寫一份評分標準，讓另一個 LLM 照著標準幫你打分。** 這叫 LLM-as-a-Judge。

好消息是它真的有用。2023 年的一項經典研究（Zheng et al., MT-Bench 論文）發現，強模型當裁判時，與人類判斷的一致率超過 80% —— 這個數字大約等同於**兩個人類之間**的一致率。

換句話說：一個好的 LLM 裁判，跟你找另一個同事來審，準確度差不多。

壞消息是它有四種**系統性**偏誤。不是偶爾出錯，是穩定地往同一個方向歪。

## 四種偏誤

### 1. 位置偏誤（Position Bias）

給裁判看兩個答案 A 和 B，問哪個好。**它傾向選第一個。**

換句話說，把同樣兩個答案交換順序再問一次，它可能給出相反的答案。

**怎麼防：** 兩種順序都跑，取平均。如果兩次結論不一致，代表這一題裁判其實沒有判斷力，只是在猜。

### 2. 冗長偏誤（Verbosity Bias）

**它偏好比較長的答案。** 即使長的那個並沒有多說什麼有用的東西。

這個偏誤特別危險，因為它會讓被評估的 Agent 學會「多寫一點就會拿高分」，然後你的 YCO 報告會越來越長、越來越囉唆，而分數持續上升。

**怎麼防：** 在評分標準裡明確寫「簡潔本身是加分項」，或者把長度正規化。更好的做法是用**二元條目**（見下方 rubric 設計），因為二元條目對長度不敏感 —— 「有沒有列出至少兩個偵測到的膚況問題」這題，寫 50 字和寫 500 字的答案是一樣的判定。

### 3. 自我偏好偏誤（Self-Preference Bias）

**它偏好自己家族模型產生的內容。**

這是四種裡最陰險的一種。如果你用 Claude 生成報告、又用 Claude 當裁判，裁判會系統性地給高分。你的 pass rate 會很漂亮，而且完全是假的。

RQGM 論文對這件事有具體測量：最強的基準審查器對 **AI 寫的論文**的接受率，高達對人類寫的論文的 **1.91 倍**。同樣品質，只因為是 AI 寫的就更容易被接受。

**怎麼防：** **用不同家族的模型當裁判。** 這是你這整套系統裡最便宜、效果最大的一條規則。生成用一家，評分用另一家。

### 4. 校準不良（Poor Calibration）

**它說「我 90% 確定」的時候，實際正確率可能只有 60%。** 它的信心程度跟實際準確度對不上。

**怎麼防：** 不要問它「你多有信心」，改問它「這一條有沒有通過，並引用原文證據」。要求引證據，會逼它停止憑感覺。

## 從偏誤反推：rubric 的三條設計規則

上面四種偏誤，其實可以用三條寫作規則擋掉大半。

### 規則一：條目要二元（Binary）

**壞：** 「這份報告的建議是否恰當？」
**好：** 「每一個推薦的產品，是否都對應到報告中明確提到的一個膚況問題？（是／否）」

二元條目不受長度影響、不受語氣影響，而且兩個人（或兩次執行）比較容易得到相同結果。

### 規則二：證據約束（Evidence-Bounded）

要求裁判**只能根據眼前的輸出做判斷，並且引用原文**。

```
輸出格式：
{ "criterion": "每個推薦都對應到偵測到的問題",
  "verdict": "fail",
  "evidence": "報告推薦了『深層修護面膜』，但偵測結果只有毛孔與泛紅，
               沒有任何一項對應到『修護』。" }
```

強制引證據，可以擋掉裁判自己腦補上下文的「幻覺性判定」。

### 規則三：結合式接受（Conjunctive）

**所有條目都通過，才算 accept。** 不要用加權平均。

為什麼？因為加權平均允許「一項嚴重錯誤被幾項小優點抵銷」。一份編造了不存在產品的報告，不該因為語氣親切就及格。

## 動手：改寫一條

拿你 Lesson 0 那三個案例其中一個，把你的「為什麼」改寫成一條**二元、可引證據**的 rubric 條目。

範例轉換：

| 原始（模糊） | 改寫（二元可驗證） |
|---|---|
| 播放體驗要流暢 | 切換 MV 時，首幀出現時間 < 300ms |
| 報告語氣要親切 | 報告中沒有出現「嚴重」「病變」「異常」等醫療警示用語 |
| 建議要有針對性 | 每個推薦產品都對應到報告中明確列出的膚況問題 |

## 常見誤解

**誤解：「用最強的模型當裁判就好了。」**
最強的模型一樣有這四種偏誤。強模型只是比較準，不是比較沒偏見。**跨家族**比**用更強的模型**重要。

> **檢核點：** 說出四種偏誤的名字，以及每一種對應的防禦手段。

# Lesson 3 · 從 spec 到 rubric：你早就會了（1.5 小時）

## 核心洞察

你 Notion 裡那份「Claude Project Scaffold」寫著一句話：

> *State, in one line, how you will VERIFY the work.*

**那句話就是 rubric 的定義。**

一條 spec 的驗收條件，和一條 rubric 條目，是同一個東西的兩個名字：

| Spec 世界 | 評估世界 |
|---|---|
| 驗收條件（Acceptance Criteria） | Rubric 條目（Criterion） |
| TBD-MV-01 已解決 | 這個案例 pass |
| Spec review 打回 | 判定 reject |
| Spec v1.2 | Rubric version 2 |
| Handoff 給 RD | 把 rubric 交給 judge 執行 |

所以你不是在學一個新技能。你是在學**如何把一個你已經每天在做的動作，寫成機器可以重複執行的形式**。

## 兩種寫法，挑一種用熟

### EARS 句型（適合功能規格）

Easy Approach to Requirements Syntax。基本結構：

```
WHEN <觸發條件>, THE <系統> SHALL <可觀察的行為>
```

範例：

```
WHEN 使用者在 MV 播放中切換歌曲,
THE 播放器 SHALL 在 300ms 內顯示新 MV 的首幀。
```

### Given / When / Then（適合流程與 Agent 行為）

```
GIVEN <前置狀態>
WHEN <發生的事>
THEN <應該觀察到的結果>
```

範例：

```
GIVEN 膚況偵測回傳了「毛孔 0.7、泛紅 0.4」
WHEN Agent 生成報告
THEN 報告中每一個推薦產品，都對應到這兩項其中之一
```

**兩種都可以，挑一種用到熟為止。** 混用會讓後面的 rubric 難以維護。

## 一個可驗證條件的四個特徵

拿任何一條你寫的驗收條件，用這四題檢查：

1. **有沒有一個明確的觸發時機？**（什麼時候要檢查這件事）
2. **要觀察的東西，能不能在 10 秒內用眼睛或一個指令確認？**
3. **兩個不同的人來檢查，會得到相同結論嗎？**
4. **它是二元的，還是需要打分數？**（二元優先）

四題都過，這條就可以直接變成 rubric 條目。

## 動手：改寫五條（本課主要作業）

打開你的 YCM spec，找 **5 條已經解決的 TBD 決議**。

對每一條：

1. 抄下原始的決議文字
2. 用上面四題檢查它
3. 如果沒過，改寫成 EARS 或 Given/When/Then

做一個三欄表格：

```
| TBD ID | 原始決議 | 改寫後（可驗證版） | 沒過的是第幾題 |
```

**這份表格是 Lesson 5 的輸入。** 你等一下要把它餵給你的第一隻 Agent。

## 常見誤解

**誤解一：「所有東西都能寫成二元條件。」**
不能。有些東西本質上是程度問題（例如「這段文案吸引人嗎」）。做法不是硬掰成二元，而是**拆解**：把「吸引人」拆成「開頭 15 字內有具體利益」「沒有出現三個以上的形容詞堆疊」等等可檢查的代理指標。

**誤解二：「寫越細越好。」**
不是。一條 rubric 有 5–7 個條目通常剛好。超過 10 條，裁判的一致性會開始下降，而且你自己也維護不動。

> **檢核點：** 你手上有一份 5 列的改寫表格。有的話就往下走。

# Lesson 4 · 論文閱讀協議（1.5 小時）

**現在，而且只有現在，你可以打開那篇論文了。**

論文位置：https://arxiv.org/abs/2606.26294

## 為什麼要等到現在

因為你現在有了三樣東西，是四天前沒有的：

1. 你自己的判斷素材（Lesson 0）
2. 結果 vs 過程的分辨能力（Lesson 1）
3. 對 judge 偏誤的認識（Lesson 2）

論文裡有一半的內容，是在解決你**已經知道存在**的問題。有了這三樣，你讀的時候會不斷有「喔，這個就是在講那件事」的感覺 —— 那才是有效的閱讀。

## 三次掃描法

不要從第一頁讀到最後一頁。分三次，每次目標不同。

### 第一次掃描（20 分鐘）· 只求知道「它在主張什麼」

**只讀這些：**
- Abstract
- Introduction（§1）
- **所有圖的標題與說明文字（figure captions）** ← 很多人跳過，但這是資訊密度最高的地方
- Conclusion

**讀完要能回答：**
- 這篇論文說「現有做法」有什麼問題？
- 它提出的解法，一句話是什麼？
- 它宣稱改善了什麼？改善多少？

**不要做的事：** 不要停下來查任何一個看不懂的名詞。第一次掃描的目的是取得地圖，不是理解細節。

### 第二次掃描（40 分鐘）· 知道「每一節在做什麼」

**做法：** 把目錄抄下來，每一節旁邊寫一句話「這節在解決什麼問題」。

你可以只讀每節的第一段和最後一段，通常就夠了。

**遇到公式：跳過。** 真的，跳過。你要的是那節的**主張**，不是推導。

### 第三次掃描（30 分鐘）· 只深讀四個地方

這四個地方是你這六週真正會用到的。其他都可以先不管。

| 讀哪裡 | 你要拿走什麼 |
|---|---|
| **Controlled Utility Evolution 那節** | 「紀元」是什麼、為什麼要在邊界才換評估器 |
| **Selective Erasure 那節 + Figure 3** | 為什麼不擦除舊分數，搜尋會被舊排名「釘死」（ρ ≥ 0.90） |
| **§5 對抗性除偏 + Figure 6** | AI 裁判過度接受 AI 內容，以及怎麼修 |
| **四個 Anchor 的介紹段落** | Polyglot / APReS / IMO-GradingBench / CRAVE 各自在測什麼 |

## 符號對照表：把數學翻成人話

論文裡的符號，這樣讀：

| 符號 | 唸法 | 人話 |
|---|---|---|
| `a` | agent | 存檔裡的**一個版本** |
| `w_a` | workspace of a | 那個版本的**工作空間**（程式碼 + 提示詞） |
| `E_m` | evaluator m | **第 m 版的評分標準／裁判** |
| `S_a`, `F_a` | successes, failures | 那個版本的**成功次數、失敗次數** |
| `CMP(a)` | clade metaproductivity | 「這個版本**連同它所有後代**的總成功率」 |
| `BB_ε(a)` | epsilon best-belief | 「**保守估計**：我有 95% 把握，真實成功率至少有這麼高」 |
| `I⁻¹_ε(·,·)` | inverse regularized incomplete beta | 就是上面那個保守估計的計算工具。**不用懂，會用就好** |
| `N_t^α ≥ \|T_t\|` | expansion gate | 「什麼時候該長出新版本，而不是繼續測舊的」 |
| `Erase_m` | erase operator | 「把跟舊裁判有關的分數作廢」 |
| `ρ`（在 Spearman 那裡） | rho | **排名相關係數**。1.0 = 排名完全沒變 |
| `ρ`（在檢查點那裡） | rho | **完全不同的東西** —— 檢查點的間距倍數（論文用 2） |

> ⚠️ 最後兩列請特別注意：**論文用 `ρ` 表示兩個完全不同的東西**。看到 ρ 要先確認上下文。這種一符多義在論文裡很常見，不是你看錯。

## 這篇論文的可信度：讀之前先知道

這件事很重要，避免你把不該當真的東西當真：

**這是一篇 2026 年 6 月的 preliminary preprint（作者自己這樣定義）。** 單次執行、搜尋視野短。它的**概念**是可靠的，但**所有數字都應該視為暫定**。

另外，你手上那份中文摘要有兩個地方是錯的：

- **「13.0 倍成本削減」在論文裡不存在。** 那是虛構的數字。真實最大倍數約 3 倍。
- **「Nemotron 3 Ultra」名稱錯誤。** 論文用的是 Nemotron 3 Super 120B，只出現在附錄的消融實驗，而且論文明講那個路由「從未被觀察到實際發生」。

**這件事本身就是一課：** 二手摘要會夾帶。你剛學的「證據約束審查」原則 —— 只根據眼前的原文做判斷、要求引證據 —— 第一個該用在你自己的閱讀上。

## 動手

三次掃描做完後，寫一段 **150 字以內**的摘要，用你自己的話，不看論文，回答：

> RQGM 想解決什麼問題？它的解法是什麼？我打算從中拿走哪一個想法用在我的工作上？

寫不出來就再掃一次第一次掃描。寫得出來，代表你真的讀懂了。

> **檢核點：** 你有一段 150 字的自述摘要，而且沒有照抄論文原句。

# Lesson 5 · 環境設置 + 第一隻 Agent（4 小時）

這一課是動手，不是概念。

## Part A · 環境（1 小時）

三件事，照順序做：

1. **Supabase** — 到 supabase.com，把你其中一個暫停的專案恢復（或開新的，選 ap-southeast 區）。到 Settings → API 拿 `Project URL` 和 `anon public key`，存到記事本。
2. **Vercel** — 到 vercel.com 確認你能登入。這步先不用建專案。
3. **Notion Integration Token** — 到 notion.so/my-integrations 建一個 internal integration，拿到 token。然後回到你的 `[PF] Tasks Database` 頁面，右上 ⋯ → Connections → 加入你剛建的 integration。**這步很多人漏掉，漏了 API 會回 404。**

## Part B · 第一隻 Agent：Spec-Resolution Judge（3 小時）

**這隻 Agent 只做一件事：** 判斷你的 spec 決議有沒有包含「可在 10 秒內驗證的條件」。

它會用到你 Lesson 3 做的那份五列表格 —— 但這次是讓 AI 來判，然後你去對照它跟你的判斷差多少。

### 開始前先想 60 秒

在跑之前，先自己預測：**你那 5 條決議裡，你覺得 AI 會判幾條 FAIL？**

寫下數字。等等對照。這個動作叫做預測 - 對照，是讓學習真正發生的關鍵步驟 —— 只有在你的預測被打臉的時候，你才會真的記住。

### 執行

把「工具包」分頁裡的第一段 prompt 貼進 Claude Code（或直接用下面這段），然後把你 Lesson 3 的表格內容貼給它。

```
GOAL: Build a small evaluation agent called "spec-judge" that grades whether my
resolved YCM spec items actually meet a verifiable acceptance criterion. I drive
Claude Code and review code — keep it a single readable TypeScript script, no framework.

INPUT: I will paste 8-12 of my real resolved TBD-items. Each has: an ID
(e.g. TBD-MV-01), the resolution text, and (if present) an acceptance/verification line.

WHAT TO BUILD:
1. A script `spec-judge.ts` that takes a JSON array of items and, for each, asks an
   LLM judge to decide PASS/FAIL on this single question: "Does this resolution
   contain a criterion that a reviewer could verify in under 10 seconds by looking
   at the product or code?"
2. The judge must output strict JSON: { id, verdict: "PASS"|"FAIL",
   reason: "<one sentence>", suggested_criterion: "<if FAIL, a rewrite that WOULD
   be verifiable, in EARS or Given/When/Then form>" }.
3. Use a model from a DIFFERENT family than whatever wrote the specs, to reduce
   self-preference bias. State which model you're using and why.
4. Print a summary table: PASS count, FAIL count, and the list of suggested_criteria
   for the fails.
5. Save the output to `spec-judge-report.md`.

CONSTRAINTS:
- Do NOT touch any other files. This is a standalone artifact.
- Before writing code, restate in ONE line how you will VERIFY the script works,
  then write a 2-line sample input and show me the expected output shape.

ACCEPTANCE CRITERIA (my rubric for YOUR work):
- The script runs on my pasted items without errors.
- Every FAIL comes with a concretely better, verifiable criterion.
- The report is a markdown file I can skim in 60 seconds.
```

### 執行後最重要的一步

**不要只看報告就收工。** 做這件事：

1. 你的預測是幾條 FAIL？實際是幾條？
2. 逐條對照：**AI 的判斷和你的判斷，哪幾條不一樣？**
3. 對每一條不一樣的，問自己：**是 AI 錯了，還是我的標準其實沒說清楚？**

第 3 題是這整週最有價值的一題。

如果 AI 判 FAIL 而你覺得該 PASS，通常代表**你腦中有一個沒寫出來的補充條件**。把它挖出來寫下來 —— 那就是你 rubric 缺的那一條。

### 把結果記進台帳

打開你的 RQGM 控制台 → 台帳分頁：

- 每一條決議加一筆案例（代號用 TBD ID）
- 「我的判定」填你自己的判斷
- 「J 接受 / J 拒絕」填 AI 的判斷
- 你最有把握的那幾條，標成**錨點**

記完之後，首頁的 κ 就會亮起來。**那個數字就是「AI 這把尺跟你這把尺有多像」。**

現在還不用管它是多少 —— Week 2 才是要把它拉到 0.6 以上的時候。這週只要看到它出現就好。

> **檢核點：** 你有一份 `spec-judge-report.md`，台帳裡有至少 8 筆案例，首頁 κ 有數字。

# 本週自我檢核

不要回頭翻。先答，再對答案。

1. 為什麼「只看結果」的評估會系統性**高估** Agent 的能力？
2. LLM 裁判的四種偏誤是哪四種？
3. 四種偏誤裡，哪一種的防禦手段最便宜、效果最大？那個手段是什麼？
4. 為什麼 rubric 要用「結合式接受」（全部通過才算過），而不是加權平均？
5. 一條可驗證的驗收條件，要通過哪四題檢查？
6. `CMP(a)` 用人話講是什麼？
7. `BB_ε(a)` 用人話講是什麼？它為什麼比原始通過率好？
8. 讀論文的三次掃描，每一次的目標分別是什麼？
9. 你手上那份中文摘要有哪兩個地方是錯的？
10. 「選擇性擦除」如果不做，會發生什麼事？

---

## 答案

1. 因為 Agent 可能靠運氣或跳過必要步驟達成正確結果。只看最終產物，你看不出它的過程是壞的，直到遇到邊界案例才爆炸。
2. 位置偏誤、冗長偏誤、自我偏好偏誤、校準不良。
3. **自我偏好偏誤**。手段是**用不同模型家族當裁判** —— 生成用一家、評分用另一家。
4. 因為加權平均允許嚴重錯誤被小優點抵銷。一份編造不存在產品的報告，不該因為語氣好就及格。
5. (a) 有明確觸發時機 (b) 10 秒內可用眼睛或一個指令確認 (c) 兩個人檢查會得到相同結論 (d) 是二元的。
6. 「這個版本連同它所有後代的總成功率」—— 判斷一個版本要看它的家族表現，不是它自己的分數。
7. 「我有 (1−ε) 的把握，真實成功率至少有這麼高」的保守下限。比原始通過率好，是因為它不會被小樣本騙 —— 1 勝 0 敗的「100%」在保守估計下只有約 22%。
8. 第一次：知道它在主張什麼（abstract + intro + 圖說 + conclusion）。第二次：知道每一節在做什麼。第三次：只深讀你會用到的四個地方。
9. (a)「13.0 倍成本削減」是虛構的，論文中不存在。(b)「Nemotron 3 Ultra」名稱錯誤，實際是 Nemotron 3 Super 120B，且論文說該路由從未實際發生。
10. 搜尋會被舊排名「釘死」（Spearman ρ ≥ 0.90），新的、更嚴格的評分標準無法重新排序任何東西 —— 換了尺等於沒換。

**答對 8 題以上：** 可以進 Week 2。
**答對 5–7 題：** 回去重看答錯的那一課的「核心概念」段落，30 分鐘就好。
**答對 4 題以下：** 大概率是 Lesson 1 和 2 讀太快。這兩課是後面所有東西的地基，值得重來一次。

# 你這週結束時應該能說出的五句話

如果有人問你「你在學什麼」，你應該能不看筆記講出這五句：

1. **評估有兩層：結果和過程。只看結果會高估 Agent 的能力，因為它可能靠運氣對。**
2. **LLM 可以當裁判，準確度接近人類之間的一致率，但它有四種系統性偏誤 —— 其中最危險的是它偏袒自己家族的產出。**
3. **好的評分條目是二元的、要求引用證據的、而且必須全部通過才算過。**
4. **我寫 spec 的驗收條件，跟寫 rubric 是同一件事。我已經有這個技能，只是沒有把它變成可重複執行的形式。**
5. **RQGM 的核心主張是：固定的評分標準遲早會被鑽漏洞，所以標準必須有紀律地演化 —— 用錨點守住方向，用紀元守住比較基準。**

第 5 句是這整六週的中心。如果只能記一句，記這句。

Week 2 你會把這週的臨時判斷，變成**有版本、可重跑、有錨點守著**的東西：
